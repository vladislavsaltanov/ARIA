# BUG-2026-09-16T190000: файлы с кириллицей в пути не открываются на Windows

## Problem

Actual: файл с русскими буквами в имени/папке/пути не импортируется и не играет на Windows (пример `C:\Музыка\Проект 1\Фоновая музыка\Трек №1.mp3`). На macOS/Linux всё работает.

Expected (ТЗ 3.2): Unicode-пути везде: импорт файлов/папки, DnD, воспроизведение, сохранение/открытие проекта, экспорт/импорт, сценарии.

Repro (Windows): положить трек по пути с `№`/кириллицей → импорт «файлы не распознаны», релинк false, LUFS NaN.

Security impact: NONE. Локальные пути, новая attack surface отсутствует (тот же fopen, шире кодировка).

## Root Cause Analysis

Путь: UI отдаёт Unicode-путь → managed P/Invoke маршалит как UTF-8 → нативный шим зовёт narrow open → рантайм Windows трактует байты как ANSI codepage.

Почему падает (проверено чтением кода, scout-отчёт в сессии):

1. Главная дыра: шим принимает только `const char*` и зовёт narrow open. Managed шлёт UTF-8. На Windows narrow open идёт в ANSI codepage: символы вне codepage (`№` U+2116 нет даже в CP1251, вся кириллица мимо на CP1252) — всегда fail. Библиотека декодера уже содержит wide-вариант open, шим его не использует.
2. Маскировка: при ANSI-провале файл существует → диагностика отдаёт Undecodable вместо Missing, вводя в заблуждение.
3. Контрибьютор: managed и нативные контракты кодировки нигде не зафиксированы; unicode-тестов ноль.
4. Смежное (не блокер): строковый дедуп путей ordinal — при смене NFC/NFD-нормализации (macOS APFS) возможны дубли. Отдельным срезом при дёшево.

Не регрессия. Платформенный дефект (матрица ADR-0004: Windows непроверяем в этой среде).
